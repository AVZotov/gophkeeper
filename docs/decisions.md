# GophKeeper — архитектурные решения

Документ описывает принятые решения.
Требования — в [technical-spec.md](technical-spec.md).

## 1. Модель безопасности: zero-knowledge

Данные пользователя шифруются **на клиенте**. Сервер хранит только шифротекст
и служебные поля и **не имеет ключа расшифровки**. Утечка базы сервера не влечёт
за собой катастрофических последствий: содержимое записей остаётся закрытым.

Транспорт дополнительно защищён TLS: по каналу идут токены и служебные запросы,
которые тоже не должны быть видны.

## 2. Ключи

Четыре понятия:

| Название | Что это | Где живёт |
|---|---|---|
| пароль | мастер-пароль, который вводит пользователь | только в голове пользователя |
| ключ данных | случайные 256 бит, шифруют все записи | только в памяти клиента |
| конверт | ключ данных, зашифрованный ключом из пароля | на сервере |
| ключ для входа | доказывает серверу знание пароля | сервер хранит только его хеш |

Как они связаны:

```
пароль + соль ──Argon2id──▶ мастер-ключ (только в памяти клиента)
                               │ HKDF (crypto/hkdf)
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
            ключ-обёртка               ключ для входа
                 │                           │
   открывает конверт → ключ данных   на сервер; сервер хранит хеш
```

- **Пароль никогда не покидает клиент.** Сервер получает только ключ для входа,
  из которого нельзя восстановить ни пароль, ни ключ-обёртку.
- **Соль** — случайная, создаётся при регистрации и при смене пароля, хранится
  на сервере. Она не секретна: изолирует пользователей друг от друга, чтобы
  утечку базы нельзя было взломать одной заранее посчитанной таблицей.
- **Argon2id** (`golang.org/x/crypto/argon2`) — медленная функция,
  делает перебор пароля при утечке базы дорогим.
- **Конвертное шифрование.** Ключ данных генерируется **один раз при
  регистрации**, заворачивается ключом-обёрткой (AES-256-GCM) и хранится на
  сервере. Новое устройство при входе получает соль и конверт и открывает его
  паролем.
- **Смена пароля** перезаворачивает тот же ключ данных новым паролем и
  обновляет соль и хеш ключа для входа. **Записи не перешифровываются.**

Подход повторяет схему Bitwarden («protected symmetric key»).

## 3. Шифрование записей

- **AES-256-GCM** (стандартная библиотека), ключ — ключ данных.
- Случайный 12-байтовый nonce на каждое шифрование, хранится перед шифротекстом.
- **UUID записи передаётся как AAD**: шифротекст одной записи нельзя незаметно
  подставить под другую, клиент обнаружит подмену при расшифровке.

## 4. Содержимое записи

Перед шифрованием запись упаковывается в **protobuf-сообщение** с `oneof` по
типам: логин/пароль, текст, файл, банковская карта. У всех типов есть общее
поле метаинформации и название.

- Отдельный клиентский `.proto`: сервер этот формат не видит и не знает о нём.
- Protobuf выбран за типизацию, бинарные данные без base64 и эволюцию без
  поломок: новый тип (например, OTP) добавляется новым полем.
- Opaque API protobuf, как и в сервисном контракте: рекомендуемый подход для
  нового Go-кода (<https://go.dev/blog/protobuf-opaque>).

## 5. Протокол

- **gRPC поверх TLS.** Клиент — программа на Go, общий `.proto` для клиента и
  сервера, бинарные данные передаются как `bytes`. Закрывает необязательную
  функцию ТЗ «бинарный протокол».
- Сгенерированный код — **Opaque API** (`edition = "2023"`,
  `api_level = API_OPAQUE`): только билдеры, сеттеры и геттеры.
- Лимит размера gRPC-сообщения явно поднят под лимит файла (раздел 12).

## 6. Аутентификация

- При входе сервер проверяет ключ для входа и выдаёт **JWT**
  (`github.com/golang-jwt/jwt/v5`).
- Токен передаётся в метаданных `authorization: Bearer <token>`, проверяется
  interceptor'ом; ID пользователя кладётся в контекст. Без токена или с
  невалидным — `codes.Unauthenticated`.
- Клиент хранит токен на диске между командами. Просроченный токен клиент
  обновляет сам: когда пользователь вводит пароль, из него выводится и ключ
  для входа.

## 7. Что сервер видит о записи

В открытом виде только служебные поля:

| Поле | Зачем |
|---|---|
| UUID записи | адресовать запись |
| ID владельца | отдавать запись только хозяину |
| ревизия | синхронизация и конфликты |
| признак удаления | чтобы удаление тоже синхронизировалось |

Тип, название, метаинформация и данные — **один зашифрованный блок**. Названия
и метаданные («Сбербанк», «клиника») — тоже личные данные.

## 8. Синхронизация

- У каждого пользователя на сервере есть **сквозной счётчик ревизий**. Любое
  изменение записи (создание, правка, удаление) получает следующую ревизию.
- Клиент помнит последнюю увиденную ревизию и запрашивает «всё, что новее».
  Передаются только изменения.
- Ревизии выдаёт сервер, часы устройств ни на что не влияют.
- Удаление — пометка-«надгробие» (tombstone), строка физически не стирается,
  иначе другие устройства не узнают об удалении.

## 9. Конфликты

- **Оптимистичная блокировка по ревизии.** Клиент сообщает, от какой ревизии
  он исходил. Совпадает с текущей — правка принимается. Не совпадает —
  `codes.Aborted` и текущая версия записи.
- Сервер конфликт только **обнаруживает**: объединить два шифротекста он не
  может. Разрешает конфликт клиент.
- Клиент сначала сравнивает шифротекст сервера со своим. **Совпадают байт в
  байт** — это своя же правка, у которой потерялся ответ; конфликт не
  показывается.
- Иначе клиент **сразу показывает пользователю обе версии**: оставить свою,
  оставить с сервера, отмена. Без интерактивного ввода — ошибка с подсказкой,
  локальная правка сохраняется. Данные не теряются.

## 10. Ретраи

- **Встроенная политика ретраев gRPC** (service config): повтор при
  `Unavailable`, экспоненциальная пауза со случайным разбросом, ограниченное
  число попыток.
- Повтор **идемпотентен**: отправляются те же зашифрованные байты из локальной
  базы, без повторного шифрования (иначе nonce дал бы другие байты).
- Нет связи после всех попыток — правка остаётся в локальной базе с отметкой
  «не отправлено», пользователь видит понятное сообщение.

## 11. Клиент

### Офлайн-работа

- Локальная копия записей на **SQLite на чистом Go** (`modernc.org/sqlite`, без
  CGO). Клиент собирается под Windows, Linux и Mac.
- Хранит те же строки, что сервер, плюс отметку «изменено, не отправлено».
- На диске только шифротекст, токен, соль и ключ данных, **зашифрованный
  ключом сессии**. Ключ данных в открытом виде на диск не пишется никогда.

### Сессия

Подход взят у Bitwarden CLI (`bw unlock`):

- `gophkeeper unlock` открывает конверт паролем, шифрует ключ данных случайным
  ключом сессии и сохраняет результат на диск;
- ключ сессии выдаётся пользователю и живёт только в переменной окружения
  `GOPHKEEPER_SESSION` текущего терминала;
- команды берут ключ сессии из окружения и расшифровывают им ключ данных;
- `gophkeeper lock` завершает сессию.

### Интерфейс и конфигурация

- CLI на **Cobra**, конфигурация через **Viper**: флаги, переменные окружения с
  префиксом `GOPHKEEPER_`, файл конфигурации.
- Пути к файлам — через `os.UserConfigDir()` и аналоги, без захардкоженных путей.

## 12. Файлы

- Лимит — **10 МБ**. Файл целиком в памяти, шифруется одним сообщением AES-GCM,
  передаётся одним вызовом, без стриминга.
- Клиент проверяет размер до шифрования, сервер — размер шифротекста.
- Благодаря ревизиям файл скачивается заново только при изменении его записи.

## 13. Сервер

- **PostgreSQL**, `pgx/v5` (нативный API), миграции **goose**.
- Интеграционные тесты на **testcontainers-go** — решение по срокам сдачи;
  они закрыли бы необязательную функцию ТЗ.
- Конфигурация: флаги + переменные окружения (`caarlos0/env`) + JSON-файл,
  приоритет: env > флаги > файл > значения по умолчанию.

## 14. Общее

- **Логирование** — `log/slog`. Секреты (пароль, ключи, токены, расшифрованные
  данные) не логируются никогда; чувствительные типы реализуют
  `slog.LogValuer` и выводятся как `[REDACTED]`. `slog` выбран осознанно:
  хочу попробовать логгер из стандартной библиотеки Go. Опыт работы с zap
  у меня уже есть, а с `slog` — ещё нет.
- **Версия и дата сборки** — через `-ldflags -X`, команда `gophkeeper version`.
- **Сборка** — Taskfile: генерация proto, тесты с покрытием, линтер, `build:all`
  под Windows, Linux и Mac. По кастомному линтеру решение ещё не принято.
- **Тесты** — testify, покрытие не ниже 70%.

## 15. Необязательные функции ТЗ

| Функция | Статус |
|---|---|
| бинарный протокол | да, gRPC |
| интеграционные тесты | возможно, testcontainers-go |
| OTP | нет, возможно позже (новый тип в `oneof`) |
| TUI | нет, возможно позже |
| Swagger | нет, протокол не REST |

## 16. Открытые вопросы

Решаются по ходу работы:

- структура репозитория;
- схемы таблиц PostgreSQL и SQLite;
- список gRPC-методов;
- параметры Argon2id, алгоритм хеширования ключа для входа на сервере, срок
  жизни JWT;
- ограничение частоты попыток входа (защита от онлайн-перебора пароля);
- запуск PostgreSQL для разработки (`docker compose`);
- интеграционные тесты (testcontainers-go) — по срокам;
- кастомный линтер (multichecker по образцу спринта 7).
