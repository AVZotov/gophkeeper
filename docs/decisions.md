# GophKeeper — архитектурные решения

Документ описывает принятые решения.
Требования — в [technical-spec.md](technical-spec.md).

## 1. Модель безопасности: zero-knowledge

Данные пользователя шифруются **на клиенте**. Сервер хранит только шифротекст
и служебные поля и **не имеет ключа расшифровки**. Утечка базы сервера не влечёт
за собой катастрофических последствий: содержимое записей остаётся закрытым.

Транспорт дополнительно защищён TLS: по каналу идут токены и служебные запросы,
которые тоже не должны быть видны.

Ограничения модели описываются в README, чтобы у пользователя не было ложных
ожиданий:

- zero-knowledge защищает **конфиденциальность, а не историю**: ревизия не
  входит в AAD (раздел 3), поэтому сервер может незаметно откатить запись к
  старой версии или скрыть её;
- ключ данных **не меняется** при смене пароля (раздел 2): если он утёк, смена
  пароля не помогает;
- переменную сессии видят дочерние процессы терминала (раздел 11).

## 2. Ключи

Четыре понятия:

| Название | Что это | Где живёт |
|---|---|---|
| пароль | мастер-пароль, который вводит пользователь | только в голове пользователя |
| ключ данных | случайные 256 бит, шифруют все записи | в памяти клиента; на диске только зашифрованный ключом сессии |
| конверт | ключ данных, зашифрованный ключом из пароля | на сервере и в локальной базе клиента |
| ключ для входа | доказывает серверу знание пароля | сервер хранит только его хеш; клиент — только зашифрованный ключом сессии |

Как они связаны:

```
пароль + соль ──Argon2id──▶ мастер-ключ (только в памяти клиента)
                               │ HKDF (crypto/hkdf)
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
            ключ-обёртка               ключ для входа
                 │                           │
   открывает конверт → ключ данных   на сервер; сервер хранит хеш
```

- **Пароль никогда не покидает клиент.** Сервер получает только ключ для входа,
  из которого нельзя восстановить ни пароль, ни ключ-обёртку.
- **Соль** — случайная, создаётся при регистрации и при смене пароля, хранится
  на сервере и в локальной базе клиента. Она не секретна: изолирует
  пользователей друг от друга, чтобы утечку базы нельзя было взломать одной
  заранее посчитанной таблицей.
- **Argon2id** (`golang.org/x/crypto/argon2`) — медленная функция,
  делает перебор пароля при утечке базы дорогим. Параметры — **константы в
  коде клиента**, сервер их не передаёт: иначе вредоносный сервер мог бы
  занизить их и быстро перебрать пароль по полученному ключу для входа.
  Значения — RFC 9106, второй рекомендованный вариант: t=3, m=64 МиБ, p=4,
  длина ключа 32 байта, соль 16 байт.
- **HKDF** — SHA-256, только Expand: выход Argon2id уже равномерно случаен,
  поэтому Extract не нужен (RFC 5869, §3.3). Метки info:
  `gophkeeper/v1/wrap-key` — ключ-обёртка, `gophkeeper/v1/login-key` — ключ
  для входа.
- **Хеш ключа для входа** на сервере — SHA-256, сравнение за постоянное время
  (`crypto/subtle`). Медленный хеш здесь не нужен: ключ для входа — 256 бит,
  уже полученные через Argon2id, перебирать их напрямую бессмысленно.
- **Конвертное шифрование.** Ключ данных генерируется **один раз при
  регистрации**, заворачивается ключом-обёрткой (AES-256-GCM) и хранится на
  сервере. Конверт — 60 байт: nonce 12 + зашифрованный ключ данных 32 + тег
  GCM 16, без AAD.
- **Вход на новом устройстве** — в два шага:
  1. До входа клиент получает по логину **только соль**. Для несуществующего
     логина сервер отдаёт фальшивую соль `HMAC(server_secret, login)`: она
     постоянна для логина, и по ответу нельзя узнать, есть ли пользователь.
  2. Клиент выводит ключ для входа и входит. **Конверт сервер отдаёт только
     после проверки ключа для входа**: иначе любой, кто знает логин, получил
     бы конверт и перебирал бы пароль офлайн — без утечки базы и без
     ограничения частоты попыток.
- **Смена пароля** требует **старый ключ для входа**, одного токена мало:
  украденным токеном можно было бы подменить конверт ключом-пустышкой, и
  настоящий ключ данных был бы потерян навсегда. Смена перезаворачивает тот же
  ключ данных новым паролем; соль, конверт, хеш ключа для входа и время смены
  пароля обновляются **атомарно**, одной строкой пользователя. **Записи не
  перешифровываются.**
- **Версии формата нет сознательно.** Параметры Argon2id нужны до открытия
  конверта, а версию внутри конверта контролирует сервер: по ней он мог бы
  заставить клиент перейти на слабые параметры. Смена параметров, меток HKDF
  или формата — это миграция всех пользователей; эталонный тест в
  `vaultcrypto` не даст изменить их незаметно.

Подход повторяет схему Bitwarden («protected symmetric key»).

## 3. Шифрование записей

- **AES-256-GCM** (стандартная библиотека), ключ — ключ данных.
- Случайный 12-байтовый nonce на каждое шифрование, хранится перед шифротекстом.
- **UUID записи передаётся как AAD**: шифротекст одной записи нельзя незаметно
  подставить под другую, клиент обнаружит подмену при расшифровке.
- UUID записи — 16 байт (бинарная форма RFC 9562), в контракте `bytes`; AAD —
  эти 16 байт.
- Формат шифротекста записи: nonce 12 + шифротекст (длина открытого текста) +
  тег GCM 16, то есть на 28 байт длиннее открытого текста.

## 4. Содержимое записи

Перед шифрованием запись упаковывается в **protobuf-сообщение** с `oneof` по
типам: логин/пароль, текст, файл, банковская карта. У всех типов есть общее
поле метаинформации и название.

- Отдельный клиентский `.proto`: сервер этот формат не видит и не знает о нём.
- Protobuf выбран за типизацию, бинарные данные без base64 и эволюцию без
  поломок: новый тип (например, OTP) добавляется новым полем.
- Opaque API protobuf, как и в сервисном контракте: рекомендуемый подход для
  нового Go-кода (<https://go.dev/blog/protobuf-opaque>).

## 5. Протокол

- **gRPC поверх TLS.** Клиент — программа на Go, общий `.proto` для клиента и
  сервера, бинарные данные передаются как `bytes`. Закрывает необязательную
  функцию ТЗ «бинарный протокол».
- Сгенерированный код — **Opaque API** (`edition = "2024"`, в нём Opaque API
  включён по умолчанию, опция `api_level` не нужна): только билдеры, сеттеры
  и геттеры.
- Поля без явного присутствия (`features.field_presence = IMPLICIT`): ни в
  одном поле контракта нулевое значение не отличается от «не задано».
  `Has…` остаются только у `oneof`.
- Лимит размера gRPC-сообщения явно поднят под лимит файла (раздел 12).
- Контракт — `api/gophkeeper/v1/`, два сервиса:

| Метод | Запрос → ответ | Токен |
|---|---|---|
| `Auth.GetSalt` | login → salt | нет |
| `Auth.Register` | login, salt, login_key, envelope → пусто | нет |
| `Auth.Login` | login, login_key → token, envelope | нет |
| `Auth.ChangePassword` | old_login_key, new_salt, new_login_key, new_envelope → пусто | да |
| `Vault.Pull` | since → records[], has_more | да |
| `Vault.Push` | id, base_revision, ciphertext, deleted → revision | да |

- Запись в `Pull`: id, revision, deleted, ciphertext. Курсор — ревизия:
  следующая страница запрашивается с `since` = ревизия последней записи.
  Размер страницы определяет сервер.
- `Push` при конфликте возвращает `codes.Aborted`, текущая версия записи —
  в status details. Для новой записи `base_revision = 0`.
- Токен выдаёт только `Login`: после `Register` и `ChangePassword` клиент
  входит через `Login`.
- Клиент доверяет серверу через **CA**: путь к сертификату CA задаётся при
  `login` (раздел 11). Сертификаты для разработки создаются через `openssl`
  задачей Taskfile.

## 6. Аутентификация

- При входе сервер проверяет ключ для входа и выдаёт **JWT** с **коротким
  сроком жизни** (`github.com/golang-jwt/jwt/v5`).
- Токен передаётся в метаданных `authorization: Bearer <token>`, проверяется
  interceptor'ом; ID пользователя кладётся в контекст. Без токена или с
  невалидным — `codes.Unauthenticated`.
- **Тихий повторный вход.** При `unlock` ключ для входа сохраняется на диск,
  зашифрованный ключом сессии, как и ключ данных (раздел 11). Истёк токен —
  клиент сам входит заново с этим ключом, пароль не спрашивается.
- **Отзыв токенов.** У пользователя хранится время смены пароля; interceptor
  отклоняет токены, выданные раньше него. Зачем: JWT сам по себе не
  отзывается, а токен лежит на диске клиента. С украденным токеном можно
  пометить удалёнными все записи; надгробие стирает шифротекст (раздел 8), и
  удаление расходится на все устройства — данные потеряны. Смена пароля должна
  такой токен обезвреживать. Устройство, сменившее пароль, обновляет ключ для
  входа в своей сессии и входит заново тихо.
- Interceptor сравнивает `iat` токена со временем смены пароля, **усечённым
  до секунды**: `iat` в JWT хранится в секундах, а время смены — с
  микросекундами. Без усечения токен тихого входа, выданный в ту же секунду,
  что и смена пароля, был бы отклонён.

## 7. Что сервер видит о записи

В открытом виде только служебные поля:

| Поле | Зачем |
|---|---|
| UUID записи | адресовать запись |
| ID владельца | отдавать запись только хозяину |
| ревизия | синхронизация и конфликты |
| признак удаления | чтобы удаление тоже синхронизировалось |

Тип, название, метаинформация и данные — **один зашифрованный блок**. Названия
и метаданные («Сбербанк», «клиника») — тоже личные данные.

## 8. Синхронизация

- У каждого пользователя на сервере есть **сквозной счётчик ревизий**. Любое
  изменение записи (создание, правка, удаление) получает следующую ревизию.
- Счётчик хранится **в строке `users`** и увеличивается через
  `UPDATE ... RETURNING` в той же транзакции, что и изменение записи. Не
  `SEQUENCE`: значения последовательности выдаются сразу, а транзакции
  коммитятся в любом порядке. Транзакция с ревизией 6 может закоммититься
  раньше транзакции с ревизией 5; клиент запомнит 6 и никогда не получит 5.
  Блокировка строки пользователя выстраивает коммиты в порядке ревизий.
- Клиент помнит последнюю увиденную ревизию и запрашивает «всё, что новее».
  Передаются только изменения. Выдача **постраничная**: несколько файлов по
  10 МБ одним ответом превысили бы лимит gRPC-сообщения.
- Порядок: **сначала отправка, потом получение**. Записи с неотправленной
  правкой при получении не перезаписываются: их судьбу решает отправка
  (раздел 9).
- Ревизии выдаёт сервер, часы устройств ни на что не влияют.
- Удаление — пометка-«надгробие» (tombstone), строка физически не стирается,
  иначе другие устройства не узнают об удалении. **Шифротекст при этом
  стирается**: удалённые секреты не должны жить на сервере и в бэкапах.

## 9. Конфликты

- **Оптимистичная блокировка по ревизии.** Клиент сообщает, от какой ревизии
  он исходил. Совпадает с текущей — правка принимается. Не совпадает —
  `codes.Aborted` и текущая версия записи.
- Сервер конфликт только **обнаруживает**: объединить два шифротекста он не
  может. Разрешает конфликт клиент.
- Клиент сначала сравнивает шифротекст сервера со своим. **Совпадают байт в
  байт** — это своя же правка, у которой потерялся ответ; клиент молча
  принимает версию сервера.
- Иначе — **копия конфликта**: клиент принимает версию сервера, а свою правку
  сохраняет новой записью с «(конфликт)» в названии. Копия шифруется заново:
  у неё новый UUID, а UUID входит в AAD (раздел 3). Пользователь видит обе
  записи и сам решает, какую оставить. Данные не теряются.
- **Удаление против правки — правка побеждает:**
  - своё удаление против чужой правки — удаление отменяется, принимается
    версия сервера;
  - своя правка против чужого удаления — правка отправляется заново поверх
    надгробия и восстанавливает запись.

## 10. Ретраи

- **Встроенная политика ретраев gRPC** (service config): повтор при
  `Unavailable`, экспоненциальная пауза со случайным разбросом, ограниченное
  число попыток. Кратковременный сбой сети не должен становиться ошибкой для
  пользователя.
- Повтор **идемпотентен**: отправляются те же зашифрованные байты из локальной
  базы, без повторного шифрования (иначе nonce дал бы другие байты).
- Нет связи после всех попыток — правка остаётся в локальной базе с отметкой
  «не отправлено», пользователь видит понятное сообщение.

## 11. Клиент

### Офлайн-работа

- Локальная копия записей на **SQLite на чистом Go** (`modernc.org/sqlite`, без
  CGO). Клиент собирается под Windows, Linux и Mac.
- Хранит те же строки, что сервер, плюс отметку «изменено, не отправлено».
- **Локальное состояние**: соль и конверт (разблокировка без сети,
  обновляются при синхронизации), токен, адрес сервера, путь к CA.
- На диске только шифротекст и локальное состояние; ключ данных и ключ для
  входа — только **зашифрованные ключом сессии**. Ключ данных в открытом виде
  на диск не пишется никогда.
- Если пароль не подходит к локальному конверту, а сервер доступен, `unlock`
  получает соль и конверт с сервера (раздел 2). Ограничение в README: после
  смены пароля на другом устройстве клиент до синхронизации открывается
  старым паролем.

### Сессия

Подход взят у Bitwarden CLI (`bw unlock`):

- `gophkeeper unlock` открывает конверт паролем, шифрует ключ данных и ключ
  для входа случайным ключом сессии и сохраняет результат в файл с правами
  `0600` и **сроком жизни**;
- ключ сессии выдаётся пользователю и живёт только в переменной окружения
  `GOPHKEEPER_SESSION` текущего терминала;
- команды берут ключ сессии из окружения и расшифровывают им ключ данных;
  просроченная сессия считается закрытой;
- **одна сессия на пользователя**: новый `unlock` заменяет файл, сессии в
  других терминалах перестают работать;
- `gophkeeper lock` завершает сессию;
- `gophkeeper logout` очищает всё локальное состояние: сессию, токен,
  локальную базу и последнюю увиденную ревизию.

В README: синтаксис установки переменной для bash/zsh, PowerShell и cmd и
предупреждение, что переменную видят дочерние процессы терминала — любая
программа, запущенная из него, может прочитать её и файл сессии.

### Интерфейс и конфигурация

- CLI на **Cobra**, переменные окружения — `caarlos0/env/v11` с префиксом
  `GOPHKEEPER_`.
- Адрес сервера и путь к CA задаются при `login` и хранятся в локальном
  состоянии.
- Приоритет, как на сервере: env > флаги > сохранённое > значения по
  умолчанию.
- Пути к файлам — через `os.UserConfigDir()` и аналоги, без захардкоженных путей.

## 12. Файлы

- Лимит — **10 МБ**. Файл целиком в памяти, шифруется одним сообщением AES-GCM,
  передаётся одним вызовом, без стриминга.
- Клиент проверяет размер до шифрования, сервер — размер шифротекста.
- Благодаря ревизиям файл скачивается заново только при изменении его записи.

## 13. Сервер

- **PostgreSQL**, `pgx/v5` (нативный API, `pgxpool`), миграции **goose**.
- **Миграции применяются при старте**: они встроены в бинарник (`embed`) и
  выполняются при открытии хранилища, до первого запроса. goose — через
  Provider API, без глобального состояния; `*sql.DB` для него берётся из того
  же пула.
- PostgreSQL для разработки — `docker compose`, задачи Taskfile `db:up` и
  `db:down`.
- **Тесты хранилища — testcontainers-go** (модуль `postgres`) с тем же
  образом, что в `compose.yaml`: один контейнер на пакет, таблицы очищаются
  перед каждым тестом. Без Docker тесты падают, а не пропускаются; они входят
  в обычный прогон тестов, без build-тегов.
- Конфигурация: флаги + переменные окружения (`caarlos0/env/v11`), без файла
  конфигурации, приоритет: env > флаги > значения по умолчанию.
- Строка подключения к PostgreSQL — переменная `DATABASE_DSN` и флаг `-d`.

## 14. Общее

- **Логирование** — `log/slog`. Секреты (пароль, ключи, токены, расшифрованные
  данные, конверт и хеш ключа для входа — по последним двум можно перебирать
  пароль офлайн) не логируются никогда; чувствительные типы реализуют
  `slog.LogValuer` и выводятся как `[REDACTED]`. `slog` выбран осознанно:
  хочу попробовать логгер из стандартной библиотеки Go. Опыт работы с zap
  у меня уже есть, а с `slog` — ещё нет.
- **Версия и дата сборки** — через `-ldflags -X`, команда `gophkeeper version`.
- **Сборка** — Taskfile: генерация proto, сертификаты для разработки, тесты с
  покрытием, линтер, `build:all` под Windows, Linux и Mac. По кастомному
  линтеру решение ещё не принято. Тулчейн — **Go 1.27.2+**: в 1.27.0 есть
  уязвимости стандартной библиотеки (`govulncheck`).
- **Тесты** — testify, покрытие не ниже 70%. Сгенерированный код (`*.pb.go`)
  в покрытии не учитывается.
- **Документация** — godoc у каждого экспортированного идентификатора и

## 16. Структура репозитория

```
cmd/gophkeeper/      клиент (CLI); имя бинарника = имя команды
cmd/server/          сервер
api/gophkeeper/v1/   сервисный .proto, общий для клиента и сервера
internal/            раскладывается по мере этапов, не заранее
docs/
Taskfile.yml
```

- Клиентский `.proto` записи лежит внутри `internal/` клиента: сервер о нём
  не знает (раздел 4).
- Сгенерированный код (`*.pb.go`) **коммитится**: иначе `go install` и
  `go get` не соберут модуль.
- Перегенерация — задача Taskfile `proto`. При финальной проверке после
  перегенерации `git diff` должен быть пуст. Для этого версии `protoc` и
  плагинов зафиксированы: их номера попадают в шапку `*.pb.go`.

## 17. Открытые вопросы

- кастомный линтер (multichecker по образцу спринта 7).
